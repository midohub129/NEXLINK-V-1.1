1. التوضيح الدقيق لحالة Git والفرق مع GitHub
================================================================================
- **عدم تنفيذ Hydrogen لعمليات Git بنفسه:** لم ينفّذ Hydrogen أي `git commit` أو
  `git push` أو `git merge` أو فتح/إغلاق Pull Request أو تشغيل GitHub Actions CI
  في هذه الجلسة، التزاماً بحدود المهمة.
- **حالة البيئة المحلية:** مسار العمل هو `/app/applet`. وعند فحص `git status`
  ظهر `fatal: not a git repository (or any of the parent directories): .git`.
  لذلك لم يتمكن Hydrogen من التحقق محلياً من الفرع أو `HEAD` أو GitHub SHA أو سبب
  غياب مجلد `.git`، ولا يفترض أو يدّعي سبباً لذلك، ولا يدّعي أن اللقطة المحلية
  تمثل آخر نسخة من المستودع.
- **التمييز عن الوجود لاحقاً على GitHub:** عدم تنفيذ Hydrogen لعمليات Commit وPush
  بنفسه لا يمنع أن تكون هذه الوثائق (أو غيرها) موجودة لاحقاً في Commit على GitHub
  عبر المستخدم أو عبر عملية رفع خارجية بعد استلامها.
- **سلامة الملفات البرمجية:** لم يُعدَّل أي ملف برمجي أو اختباري، وتتطابق بصمات
  SHA-256 للملفات المرجعية الستة مع ما وُثّق في `HYDROGEN_EXECUTION_REPORT.txt` (التقرير 6).

2. التصحيح الأخير: إلزامية حاجز قاعدة البيانات (Mandatory Write Barrier)
================================================================================
المشكلة التي تم إصلاحها في التصميم:
- كانت النسخة السابقة تستخدم `writeBarrier?: IDatabaseWriteBarrier` و
  `this.writeBarrier?.assertWriteAllowed(...)`، ما كان يتيح إنشاء قاعدة بيانات
  بلا حماية عند إغفال تمرير الحاجز.

التصميم المصحَّح النهائي:
1. **`writeBarrier` إلزامي تماماً في `IndexedDbDatabase`:**
   - يقبل مُنشئ `IndexedDbDatabase({ dbName, writeBarrier })` حاجزاً إلزامياً غير
     قابل لأن يكون `undefined` أو `null`، مع حذف `?.` كلياً من `enqueueWrite()`.
   - يتحقق المُنشئ وقت التشغيل عبر `isValidWriteBarrier(options.writeBarrier)` ويرمي
     فوراً `StorageError('DB_WRITE_BARRIER_REQUIRED', ...)` عند غيابه أو عدم صلاحيته؛
     أي يستحيل إنشاء قاعدة بيانات إنتاجية دون حاجز حماية.
2. **خيار اختباري صريح ومحدود وممنوع في الإنتاج:**
   - أُضيفت دالة `createUnprotectedIndexedDbForTestsOnly(dbName, { confirmUnsafeTestOnly: 'TEST_ONLY_NO_BARRIER' })`
     التي تشترط القيمة الحرفية الصريحة وترمي `TEST_ONLY_DB_FORBIDDEN_IN_PRODUCTION`
     إذا استُدعيت في بناء Vite إنتاجي (`import.meta.env.PROD`) أو خارج بيئة اختبار Node،
     مع حظر استيرادها داخل `src/` عبر قاعدة ESLint في المرحلة 2A.
3. **مرجع واحد مشترك في `createAppContainer()`:**
   - تنشئ `createAppContainer()` مثيلاً واحداً من `RestoreCoordinator` وتمرر المرجع
     نفسه إلى `new IndexedDbDatabase({ dbName: APP_DB_NAME, writeBarrier: restoreCoordinator })`
     وإلى `executeRestoreWithPostCommitRecovery` وحراس الخدمات و`HealthMonitor`.
4. **شمول جميع معاملات الكتابة وحرية القراءة:**
   - `enqueueWrite()` خاصة (`private`) وتفحص `this.writeBarrier.assertWriteAllowed(...)`
     مرتين (قبل دخول `writeQueue` وقبل `db.transaction()` مباشرة) في جميع عمليات
     `put`, `add`, `deleteKey`, `clearStore`, و`runTransaction('readwrite')`، مع
     ربط التصريح بقدرة غير قابلة للتزوير (`WeakMap` + `symbol` قفل نشط) مقيدة
     بالجداول الأربعة (`SETTINGS`, `LINKED_DEVICES`, `SYNC_EVENTS`, `SECURITY_AUDIT`).
   - عمليات القراءة (`readAll`, `readOne`, `getMigrations`, `readonly`) لا تمر عبر
     `enqueueWrite` ولا عبر الحاجز ولا تتأثر أثناء الاستعادة.
