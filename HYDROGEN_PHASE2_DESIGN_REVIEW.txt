2. ملخص التعديلات الأربعة المدمجة في HYDROGEN_PHASE2_DESIGN.txt
================================================================================

(أولاً) إضافة حماية مركزية لقاعدة البيانات (Central Database Write Barrier):
- أين وُضعت؟ داخل `IndexedDbDatabase` (`src/infrastructure/storage/indexedDbDatabase.ts`)
  نفسه، بالتكامل مع `RestoreCoordinator` عبر واجهة `IDatabaseWriteBarrier`.
- كيف تعمل دون الاعتماد على Boolean قابل للتعديل؟
  1. تصبح `enqueueWrite()` دالة `private` وتستقبل المخازن المستهدفة وتصريحاً اختيارياً.
  2. يولّد `RestoreCoordinator.tryAcquire()` رمز قفل خاص (`symbol`) لا يُصدَّر لأي جهة،
     ويمنح `mintRestoreTransactionCapability(lockToken)` كائناً غير قابل للتزوير
     (`RestoreWriteCapability`) يُتحقق من صلاحيته عبر `WeakMap` خاص داخل المنسق.
  3. تفرض `IndexedDbDatabase` فحصين على كل عملية `put`/`add`/`deleteKey`/`clearStore`/
     `runTransaction(..., 'readwrite')` لجميع الجداول (`SETTINGS`, `LINKED_DEVICES`,
     `SYNC_EVENTS`, `SECURITY_AUDIT`):
     - الفحص 1 (تزامني قبل دخول `writeQueue`).
     - الفحص 2 (داخل `writeQueue` قبل فتح `IDBTransaction` مباشرة لالتقاط أي عملية
       دُفعت إلى الطابور قبل تفعيل القفل مباشرة).
  4. يقتصر التصريح حتى لحامله على الجداول الأربعة المستهدفة فقط (فيظل `IDENTITY`
     و`MIGRATIONS` محميين)، بينما لا تتأثر عمليات القراءة (`readAll`, `readOne`,
     `getMigrations`, `readonly` tx) إطلاقاً.

(ثانياً) إصلاح `InFlightTracker` لمنع `Unhandled Promise Rejection`:
- المشكلة السابقة: `const settled = p.finally(...)` كان ينشئ وعداً مشتقاً يرفض دون
  معالج أثناء التشغيل الطبيعي عند فشل `work()`.
- الحل النهائي: فصل `opPromise` (الذي يرجع للمستدعي بنتيجته أو خطئه الأصلي) عن
  `trackerPromise = opPromise.then(() => undefined, () => undefined).finally(() => { this.active.delete(trackerPromise); })`.
  وبذلك يظل `trackerPromise` خالياً تماماً من أي رفض غير معالج، وتُحذف العملية من
  `this.active` عند النجاح أو الفشل، وتنتظر `drain()` جميع العمليات عبر `Promise.all(Array.from(this.active))`.

(ثالثاً) إصلاح سباق `start()` و`stop()` وقواعد التعافي:
- إزالة `await this.stopPromise.catch(() => {})` نهائياً عند استدعاء `start()`.
- معالجة التداخلات الأربع (`start+start`, `stop+stop`, `start+stop`, `stop+start`)
  عبر `opEpoch` + `desiredState` + `startPromise`/`stopPromise` + `hasUnsettledDrainFailure`:
  * إذا فشل `stop()` بسبب انتهاء مهلة `drain()` (`activeCount > 0`) أو فشل فصل مستمع،
    يرفض `start()` فوراً ويبقى المحرك في `'ERROR'` مع إبقاء `inFlight.pauseAccepting()`.
  * في `container.ts`: يُمنع استدعاء `startSyncEngine()` في `catch (stopErr)` إذا كان
    السبب `BACKUP_RESTORE_DRAIN_TIMEOUT`.
  * كل عملية طويلة ومستمع يحمل `opEpoch` ويفحص `isStaleExecution(entryEpoch)` قبل أي
    تعديل لذاكرة التخزين أو طلب كتابة.
  * قواعد التعافي الصريحة: الخطأ النظيف (`activeCount === 0 && !hasUnsettledDrainFailure`)
    يسمح بـ `start()` لاحقاً؛ أما فشل التصريف فيحظر `start()` حتى تستقر جميع المهام
    المعلقة (`activeCount === 0`) وتمر عبر `recoverAfterError()`/`stop()` وتُرفع `opEpoch`،
    أو عبر إعادة تحميل التطبيق بالكامل.

(رابعاً) تشديد شروط `'HEALTHY'` في `HealthMonitor`:
- شُطبت إمكانية اعتبار الأحداث القديمة ذات الحالة `'SYNCED'` دليلاً على `'HEALTHY'`.
- لا تعود `'HEALTHY'` إلا عند تحقق الشروط الستة معاً:
  1. `syncLifecycle === 'RUNNING'` (و`databaseHealthy === true`).
  2. `transportStatus === 'CONNECTED'`.
  3. اكتمال دورة مزامنة فعلية بنجاح (`hasCompletedSyncCycleInCurrentRun === true` بعد
     `start()` واتصال النقل الحالي دون `skippedReason` ومع `failed === 0`).
  4. عدم وجود أخطاء مزامنة نشطة أو أحداث فاشلة (`failedCount === 0`).
  5. عدم وجود عملية استعادة جارية (`!isRestoreInProgress()` ولا قفل DB نشط).
  6. عدم وجود عمليات قديمة أو غير مصرفة (`staleInFlightCount === 0` و`!hasUnsettledDrainFailure`).
- تم توثيق الحاجة لتحديث الاختبار القائم `tests/unit/backupV2.test.ts:1326` في
  المرحلة 2D/2E لأن هذا الاختبار كان يفترض `'HEALTHY'` بمجرد وجود حدث `SYNCED` قديم
  بعد `start()` دون تشغيل دورة مزامنة فعلية.

3. ضمان عدم وجود كتابة متزامنة مع استعادة قاعدة البيانات
================================================================================
تتحقق الضمانة عبر ثلاث طبقات متراكبة (Defense-in-Depth):
1) بوابة التنسيق والخدمات: رفض فوري في `AppContainer` و`SyncEngine` و`DeviceManager`
   و`SettingsService` و`SecurityManager` مع إيقاف `schedulerParticipant` وفصل المستمعات
   وإجهاض طلبات HTTP عبر `AbortController` وتصريف العمليات الجارية عبر `InFlightTracker.drain()`.
2) عزل الجيل (`opEpoch`): أي مهمة قديمة معلّقة تستيقظ لاحقاً تكتشف تغيّر `opEpoch`
   أو حالة `'ERROR'`/`'STOPPED'` وتتوقف قبل لمس الذاكرة المخبأة أو طلب كتابة.
3) الحاجز المركزي في `IndexedDbDatabase` (الضمانة الحاسمة): حتى لو فلتت عملية قديمة
   أو استُدعي أي مستودع مباشرةً، فإن `enqueueWrite` يرفض كل معاملة `readwrite` قبل
   الطابور وقبل `db.transaction()` ما لم تحمل `RestoreWriteCapability` صالحة مرتبطة
   بقفل `RestoreCoordinator` النشط ومقصورة على الجداول الأربعة.
